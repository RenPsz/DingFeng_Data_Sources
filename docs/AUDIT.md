# cnfin.py 生产级审计报告

- 审计对象：`cnfin.py` v1.0.0（约 1822 行）
- 审计范围：数据口径正确性、故障路径、缓存安全、HTTP 状态管理、输入校验、并发、发布工程
- 结论版本：v1.1.0（本报告所述 P1 已全部修复并有回归测试）
- 审计方式：通读全部源码 + 离线构造上游响应复现问题 + 真实网络探测记录交叉核对

---

## 一、总结论

**v1.0.0 不满足“生产级底层数据模块”标准。** 它的 happy path 是通的，17 项 demo 也全过，但审计发现：可用性验证不等于正确性验证。真正危险的是三类问题：

1. **返回了数据，但口径不对**：请求后复权返回不复权、请求最新 N 根返回最旧 N 根、请求周线降级成日线、成交量单位不一致。
2. **返回了数据，但不完整**：长历史分页上限静默截断、批量行情部分成功、缓存键碰撞读到别的请求结果。
3. **故障语义混乱**：停牌/程序错误/网络故障都可能污染熔断，代理配置互相覆盖，pickle 缓存在目录可写场景下等于任意代码执行。

**无条件触发的 P0 为 0 项**；唯一可升级为 P0 的是“缓存目录可被不可信主体写入时的 pickle 反序列化”，v1.1 已通过改用 JSON 缓存消除。

**v1.1.0 已修复全部 P1（26 项），剩余 12 项 P2 不阻塞受控生产使用**，见第五节。

## 四、修复后的关键行为变化（调用方须知）

1. **降级链现在会“拒收”不合格数据**：缺复权、缺字段、部分批量、分页不完整都会报 `SourceError` 并尝试下一个源，而不是先返回再说。
2. **程序错误不再被降级掩盖**：传错参数、上游 schema 造成 `ValueError/TypeError` 会直接抛出；只有网络/反爬/解析类 `SourceError` 和停牌类 `NoDataError` 参与降级。
3. **`is_trade_day`、日期解析、limit/periods/freq 全部严格化**：以前“能跑”的脏输入现在会立即报错 —— 这是有意为之。
4. **旧缓存 `.pkl` 不再读取**，首次升级后会自然回源重建，无需手动迁移。
5. **`prefer` 必须是已注册且声明该能力的源**，否则 `ValueError`，不再静默忽略。

## 五、剩余风险（P2，按建议处理顺序）

| ID | 风险 | 影响 | 建议 |
|---|---|---|---|
| R-01 | `financial_statement` 原始宽表列随源不同（东财英文 key / 新浪中文科目） | 下游若不读 `attrs["source"]` 直接取列会崩 | 文档已声明；后续可为三大报表定义“核心科目白名单”列集 |
| R-02 | akshare 财务摘要的金额单位（元/万元）未做逐指标审计 | 跨源拼接时量纲可能不一致 | 用年报样本做一次单位对照表后再统一缩放 |
| R-04 | host 限速锁粒度较粗 | 高并发下不同 host 可能互相等待 | 改为 per-host lock/信号量 |
| R-05 | host 熔断状态不跨实例共享 | 多进程/多实例会各自试错一次 | 进程内可接受；跨进程需外部状态或统一网关 |
| R-06 | `router.trace` 并发时混合记录 | 观测归因略模糊 | 已限制为最近 200 条；后续每次调用生成 trace_id，按 id 分组 |
| R-07 | JSON 缓存对 pandas 特殊 dtype（Period、多级列等）保真度有限 | 复杂 DataFrame 不建议进缓存 | 当前公开返回均为平面表；新增复杂结构时改 Parquet/Feather |
| R-08 | 腾讯/新浪行情字段按位置索引，改版脆弱 | 上游改版即失败 | 已有长度校验 + health；可加 schema 版本探测 |
| R-09 | 无结构化指标输出（请求数/失败率/P95） | 线上可观测性不足 | 接入 Prometheus/OpenTelemetry 前先加内存计数器 |
| R-10 | 交易日历依赖上证指数推导，无法覆盖未来临时休市 | 极端日历事件可能滞后 | 接入交易所官方日历做交叉验证 |
| R-11 | 真实网络测试不进默认 PR 门禁 | 上游改版最早在下个定时窗口发现 | 保持当前取舍；重大改版后手动触发 `network.yml` |
| R-12 | 缺少跨源数值一致性差分测试 | 单源口径漂移可能长期未发现 | 对 K 线/财务摘要增加“双源差分 + 容差”测试 |
| R-13 | 过期缓存文件不会自动删除 | 长期无人值守时磁盘占用随查询组合增长 | 增加按总大小/数量的 LRU 清理，或定时任务调用 `clear_cache()` |
